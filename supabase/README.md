# Hosted pilot backend

This backend supports a **free student pilot**. There are no paid plans or admin application. The website remains on GitHub Pages; Supabase supplies OAuth, private history, usage-event storage, and the authenticated gateway. OpenAI `gpt-live-transcribe` handles streamed microphone audio, `gpt-transcribe` handles complete uploads, and `gpt-6-luna` provides coaching. There is no separate GPU worker or sign-in warmup. The migrations do not enable AI spending automatically.

## Set up a Supabase project

1. Enable **Google** and **Microsoft / Azure** under Authentication → Providers. Configure each provider's OAuth application and its Supabase callback URL. Disable email/password, phone, anonymous sign-in, and other identity providers. Google/Microsoft sign-in is not an approved TCU single-sign-on integration.
2. Set the Auth site URL and allow only the exact production/local callback URLs used by the website. Configure Google and Microsoft OAuth credentials in Supabase, never in browser code.
3. Link the project with `pnpm exec supabase link --project-ref YOUR_PROJECT_REF`, review the migration, then run `pnpm exec supabase db push`. Do not reset a hosted database.
4. Create an ignored `supabase/.env` from `.env.example` and configure server secrets with `pnpm exec supabase secrets set --env-file supabase/.env`. Speech reuses `COACHING_API_KEY` only when `COACHING_PROVIDER=openai`. Never put the service-role key or OpenAI key in a `VITE_` variable.
5. Run `node supabase/sync-policy.mjs` after editing the canonical coaching prompt. Then deploy with `pnpm exec supabase functions deploy rehearsal-api`. The generated prompt module is tested against the canonical Markdown to prevent drift.
6. Set the website's public Supabase URL and publishable key using the frontend deployment instructions. Public keys identify the project; they do not replace the user's verified OAuth token.

Google is already configured. When requests use only `openid`, email, and profile, Google's Testing exception permits users outside the test-user list without the seven-day authorization expiry; additional scopes void the exception. Organization restrictions still apply. A paid custom domain or published brand is not necessary for this pilot sign-in flow; production branding has separate requirements. [Google audience rules](https://support.google.com/cloud/answer/15549945?hl=en), [Supabase Google guide](https://supabase.com/docs/guides/auth/social-sign-in/auth-google).

For the pending Microsoft setup, open [App registrations](https://portal.azure.com/#blade/Microsoft_AAD_IAM/ActiveDirectoryMenuBlade/RegisteredApps). Select **New registration**, a Web application, the intended supported account types, and callback `https://cnqpaamclpdzdmyuqhuz.supabase.co/auth/v1/callback`. Follow the [Microsoft guide](https://supabase.com/docs/guides/auth/social-sign-in/auth-azure); enter client secrets directly into Supabase Auth, never the repository.

The Edge platform JWT switch is deliberately off for the public `/config` route and modern publishable keys. **Every private route independently calls Supabase `auth.getUser(token)` first.** It checks the verified subject, an OAuth authentication method, and a Google/Azure identity. Password authentication is rejected even for an account with a linked Google identity. Accounts with another linked OAuth provider are rejected; keep only Google/Azure enabled in this project.

## Request limits

Database-backed admission allows **1,200 requests per minute globally and 120 per minute per verified user**. Global admission precedes token verification; user admission follows it and precedes private work. Each Edge isolate also allows a burst of 60 requests, replenishes 10 tokens per second, and admits at most eight concurrent requests, including no more than two whole-audio operations to limit simultaneous buffer memory. Rate-limit responses use HTTP 429 with `Retry-After`. These controls complement authentication and AI budgets; they do not make free hosting immune to denial of service or platform quota exhaustion. Request/response body reads have byte limits and a 20-second deadline.

## Spending and storage controls

The initial migration starts the daily AI allowance at **zero**. The deployed pilot uses **5,000,000 microusd ($5) per day**, with 75,000 microusd per batch speech request, 60,000 per coaching request, 300,000 per live transcription session, and 10 AI admissions per student per day. A live session reserves once for its bounded 600 seconds of audio, including all streaming segments. Existing debits are not reset by a settings change. Reservations are conservative admission estimates, not vendor billing caps: resource use and provider behavior can vary. Revisit estimates when models, prices, or resource limits change. Changes are deliberate server-side updates; for example:

```sql
-- Current pilot admission allowance; not a provider billing guarantee.
update rehearsal_private.limits
set daily_budget_microusd = 5000000,
    requests_per_user_day = 10
where singleton;
```

One dollar is 1,000,000 microusd. Each AI operation reserves its configured estimate before calling a provider. All users have the same operational limits. An uncertain network failure stays debited because the upstream service may have billed it. A request ID can be replayed to retrieve its exact completed result, but cannot be reused for different input. Explicit retries after a known failure use a new request ID. Admission is atomic across gateway instances; there is no in-memory billing counter. Storage, authentication, and other infrastructure quotas are separate from the app's admission ledger.

Private storage permits **10 recordings per student and 40 total**, each at most 20 MiB, bounding admitted audio to 800 MiB. Both batch and live recordings upload through authenticated `POST /recordings/:id/audio`. The gateway verifies ownership and canonical mono 16 kHz PCM16 WAV bytes, measures duration (0.5–600 seconds), and checks the reservation **before writing to private Storage**. It records authoritative size/duration. Browser Storage inserts and overwrites are denied; only the server can upload to an exact pending reservation path. Format validation cannot determine whether valid PCM samples contain human speech.

An empty upload reservation has a **one-hour lease**; migration `202610270010_draft_upload_lifetime.sql` extends only encrypted live-draft reservations to their key's **24-hour recovery deadline**. On subsequent admission, expired pending reservations without a Storage object or active live-session lease release their recording slot; their metadata is retained and hidden from normal history. Late uploads are rejected under the same admission lock. Existing audio and completed recordings are not expired or deleted. New reservations are limited to **40 per user per UTC day, 400 globally per UTC day, and 10,000 retained metadata rows**; expiry and deletion do not replenish the daily counters. Delete saved recordings through the API to remove both object and database rows. A failed deletion remains visible for retry and continues occupying its slot.

Recordings, corrected transcripts, preparation inputs, and reports stay private until the student deletes the recording. Short-lived audio links expire after 60 seconds. Internal idempotency results are also private and cascade-delete with the recording. The usage ledger remains charged after deleting a recording; deleting history must not replenish spent AI allowance. Monitor Supabase's storage/database quotas during the pilot. No automatic purge is enabled: retained metadata and analytics caps stop further admission rather than deleting existing data. Agree on a retention/export policy before broader rollout or raising those caps.

## Recover processing after refresh

`GET /requests/:requestId` is an authenticated, read-only lookup of an already admitted request. Its response is `{requestId, recordingId, kind, state, createdAt, finishedAt, result}`. `kind` is `transcribe` or `coach`; `state` is `reserved`, `completed`, `failed`, `cancelled`, or `expired`. Only `completed` includes the exact saved result from the original transcription/coaching POST; other states return `result: null`. Polling never reserves another paid operation. A missing request, another user's request, and a deleting recording all return 404. Recovery and explicit cancellation require migrations `202610270003_request_recovery.sql` and `202610270004_request_cancellation.sql`; no internal budget or input-hash fields are exposed.

The server reports a reserved batch request as expired after the existing ten-minute admission window, without changing its job or usage debit. A still-active live session retains its longer twelve-minute lease. A browser marker saved before POST may return 404 while admission is still in flight; this does not establish that a delayed POST cannot commit. Keep uncertain batch recovery state until it can be reconciled.

Live refresh recovery calls `POST /live-sessions/:recordingId/cancel` with `{requestId}`. The gateway derives the owner from verified sign-in; clients cannot submit a user ID. Its response is `{recordingId, cancelled: true, status, audioSaved}`: `cancelled` acknowledges the cancellation request, `status` is the resulting session status (`cancelled`, `failed`, or `completed`), and `audioSaved` checks actual private audio presence. Completed/failed sessions keep their status, and saved audio is never deleted. This route remains available if live transcription is disabled.

If cancellation reaches the server before live creation, a content-free tombstone prevents the delayed start from reserving work. Cancellation and creation use the same database admission lock. Tombstones are scoped to the verified owner, so guessing another user's IDs cannot cancel or block their work. Tombstones expire after 24 hours, are capped at 100 per user and 10,000 globally, and expired entries are removed during live admission/cancellation. Existing request rate limits also apply. The original `DELETE /live-sessions/:recordingId` remains supported, but cannot protect a not-yet-created session.

Explicit batch cancellation calls `POST /requests/:requestId/cancel` with `{recordingId}` and returns `{requestId, recordingId, cancelled: true, state}`. Cancellation preserves saved audio, transcript, and feedback, releases the user's admission lock, and does not refund work already admitted. An owner-scoped tombstone also blocks a delayed batch submission that has not been admitted yet. Completed/failed requests keep their terminal state. A successful result is now committed atomically with its job state; a canceled request cannot later overwrite the saved recording.

Running gateway operations check their shared job state every two seconds and abort their provider HTTP signal when canceled. Live relays also check session state and close the matching provider socket. Live cancellation is acknowledged only after a reserved segment confirms closure or its bounded lease expires; an unconfirmed stop returns a retryable error after database cancellation has already taken effect. External providers may continue work or charge after their HTTP request is aborted; the app rejects any late result. A browser disconnect alone still allows batch work to finish for refresh recovery.

## Interactive rehearsal chat

Migrations `202610270005_interactive_chat.sql` and `202610270006_ephemeral_chat.sql` add authenticated `POST /coach-chat` for preparation, live-draft discussion, and follow-up on a saved report. The chat uses the server's OpenAI key with fixed `gpt-6-luna`, no tools, at most 800 output tokens, and a 45-second provider deadline plus bounded response reads. Students never submit a provider, model, or key. The browser sends only the message explicitly submitted; selecting a transcript passage does not call AI. Chat never edits a recording, transcript, report, or rating. Conversation context is labeled separately from evidence of spoken words when an analysis is requested and is not included in the saved report.

Chat admits one in-flight reply per verified user, six new messages per minute, and sixty per UTC day. Each reply atomically reserves **20,000 microusd ($0.02)** from the same project daily allowance as speech and analysis; it does not raise that allowance or consume a student's separate analysis-request counter. Failed and disconnected provider work is not refunded. Repeating a completed request returns a terminal conflict without rerunning AI: replies are not saved, so only an explicit new submission can request another reply. Changing input with the same ID is rejected. A 90-second job lease bounds stranded requests, and expired jobs cannot commit late replies. Chat remains usable during an active recording or analysis, subject to the shared HTTP limits and budget.

Optional saved-recording references are owner-checked before admission. Pre-recording chat does not create a fake recording. Conversation history is bounded to twelve messages and 16,000 characters; context and system instructions together have a 128 KiB UTF-8 byte cap. Messages, replies, and prompts are not persisted by this endpoint. Only request identifiers, hashes, timestamps, status, and usage counters are retained for duplicate prevention and spending controls. Migration 006 removes the prior reply-cache column and conversation metadata from saved reports and recovery copies, with database checks preventing that metadata from returning. A 10,000-row retained-job ceiling stops further admissions instead of growing storage indefinitely. Deleting a saved recording removes its linked receipts, but does not replenish usage counters. OpenAI requests use `store:false`; provider-side retention is governed by the provider's policy. These are operational pilot controls, not a guarantee against every provider or infrastructure charge.

At the verified Luna Standard rates of $0.10 per million input tokens and $0.50 per million output tokens, a conservative one-token-per-UTF-8-byte input estimate gives $0.0131072 for the 128 KiB prompt plus $0.0004 for 800 output tokens: about $0.01351 before fixed request framing, below the $0.02 reservation. Typical English is much cheaper. This assumes the configured model's current rates and short-context pricing; revisit the reservation when the model, prices, or caps change. [Official model pricing](https://developers.openai.com/api/docs/models/gpt-6-luna).

## Streaming transcription

Migration `202610270008_streaming_transcription.sql` adds owner-bound streaming claims. The browser creates a live session through the authenticated API, then connects to `/live-stream` and sends its OAuth token in the first WebSocket message, never in a URL. The gateway verifies that identity before admitting a segment or opening OpenAI's socket. Only the server holds the OpenAI key. The browser sends mono PCM16 at 24 kHz as microphone frames arrive and receives incremental text. It rotates connections after 100 seconds of audio or 95 seconds of wall time; the server independently bounds each connection to 110 seconds of audio and 120 seconds of wall time.

Each segment is claimed atomically for the verified owner, recording, original request, and sequence. The database reserves its full audio allowance before the provider connection opens. Completed segments commit authoritative provider text and the actual accepted sample count; only unused samples from a confirmed completion become available to later segments. Duplicate, interrupted, cancelled, or uncertain segments cannot silently start another paid connection. The total allowance remains 600 seconds across at most twelve segments. A failed stream keeps its complete recording available for an explicit complete-file transcription retry.

The browser saves the full recording separately as the validated private 16 kHz WAV described above. Finalization checks its duration against the server's committed streamed sample count and saves the server transcript; the browser cannot submit a replacement transcript through that operation. Account changes abort local work and discard stale responses. Recovery and cancellation always derive ownership from verified OAuth. Refresh cannot resume microphone capture from a closed page, but it reconciles existing server work and restores already saved audio and results without submitting them again.

Migration `202610270009_recording_draft_keys.sql` creates an independent random 256-bit key with each live admission for encrypted local audio recovery. Start returns the key to the verified owner; `GET /live-sessions/:recordingId/draft-key/:requestId` requires the same owner and original request. The key is never stored alongside the local ciphertext. Cancellation retains key access so refresh recovery can save the captured portion of an interrupted recording; key access expires after 24 hours. Successful audio finalization erases the server key, including for cancelled takes, while a failed save retains it for retry. Recording deletion cascades to the key. These routes return `Cache-Control: no-store`, and database clients cannot read or request keys directly.

There is no speech preparation request on sign-in and no model allocation to warm up. The old `/speech/prepare` and live chunk/preparation routes return 404. Migration 007 and its tests remain as historical bookkeeping; the gateway no longer calls its warmup functions. Complete uploads go to OpenAI's fixed transcription endpoint after canonical audio validation, with a fixed model and a prompt to preserve fillers and repetitions.

## Usage events

The frontend sends events only after the student opts in. Accepted fields are event/session UUIDs, an allowlisted event name and section, and at most 60 seconds of active time. The gateway supplies identity and receipt time. No transcript, audio, rubric, email, arbitrary URL, free-text property, or biometric inference is accepted in analytics. Events are deduplicated before counting and limited to **120 per user per minute, 1,000 per user per UTC day, 10,000 globally per UTC day, and 100,000 retained events**. Engagement values are client-reported estimates, not billing or research-grade measurements. Analytics have no browser read access or dashboard endpoint in this phase.

## Checks before enabling the hosted UI

Run `pnpm test`; with a local Supabase/Docker stack, also run `pnpm exec supabase start` and `pnpm exec supabase test db`. Linked-project SQL checks must use synthetic fixtures in rollback transactions. Database tests exercise RLS, cross-user access, direct-upload denial, exact-path leases, request/event bounds, budget idempotency, streaming sample limits, failure accounting, and inert injection payloads. Node tests exercise token verification, CORS, request admission, bounded body reads, canonical WAV validation before storage, upload retries, streaming rotation/cancellation, redacted errors, and no-content analytics.

Then verify the **real hosted integrations**: both OAuth providers; validated gateway upload from the deployed frontend; ownership isolation between two accounts; delete/retry; real live transcription across a connection rotation; real complete-file transcription; a real coaching response; and project budget exhaustion. Mocked gateway tests do not prove those external services are configured. Keep the existing public app operational until these checks pass.
