# Bark cloud speech worker

This separate service runs **Bark 3.0 Plus** on a CUDA GPU. Students do not download weights or supply a speech key. It does not use ElevenLabs. The Modal worker is deployed behind proxy authentication. GitHub Pages release `5ae65d2` uses the cloud service; Google sign-in and private history/report reopening passed on the public domain without student API-key entry. Microsoft configuration remains pending.

## Contract

`POST /transcribe` accepts a raw canonical RIFF WAV: mono, 16 kHz, PCM16, 0.5–600 seconds, at most 20 MiB. The app already produces this format. Send `Content-Type: audio/wav` and `Authorization: Bearer <BARK_WORKER_TOKEN>`. No multipart forms, URLs, compressed bodies, or user-selected models are accepted.

The authenticated gateway calls `POST /prepare` with an empty body on sign-in and before live rehearsal. It returns `{ "ready": true, "model": "bark-3.0-plus" }` after loading the reusable model. Sign-in preparation has separate database-backed admission and budget limits; live preparation belongs to its reserved rehearsal. Neither is a public keep-alive endpoint. Simultaneous preparation requests join the same empty model-loading task. An upload arriving during preparation waits for that task before starting its own exclusive inference. Audio and transcripts are never shared between requests. Canceling or timing out one waiter leaves other waiters running; when the last waiter leaves, the model preparation is stopped before cancellation is acknowledged.

Sign-in requests also carry `X-Rehearsal-Prepare-Expires`, a server-generated UTC Unix timestamp in milliseconds. The worker rejects expired deadlines before loading the model and bounds that caller's wait by the remaining time. Deadlines may be at most 150 seconds ahead. This prevents delayed model loading after the gateway's warmup has expired, although it cannot undo Modal scheduling or container boot that occurs before the request reaches the worker.

The gateway then sends sequential `POST /transcribe-live` requests, each containing 1 sample to 10 seconds of the same canonical WAV format. A final tail shorter than 0.5 seconds is padded only inside the worker; the response reports its original duration. Live silence returns an empty `text` successfully so the session can advance. Malformed audio still fails, and an entirely silent batch request still returns 422. All three inference routes share one busy gate and the same process cancellation behavior. Each request's 120-second deadline covers waiting for preparation, upload, and inference together; joining a warmup does not grant another full deadline.

The gateway identifies work with `X-Rehearsal-Request: <verified-user-uuid>:<request-uuid>`. Authenticated `POST /cancel` accepts exactly `{ "requestId": "<verified-user-uuid>:<request-uuid>" }`. It bypasses the inference gate, cancels only the matching request task, and waits for its isolated inference process to be killed before acknowledging `{ "cancelled": true }`. Another user's UUID cannot cancel a request even when its request UUID is the same. A bounded in-memory cancellation record rejects delayed matching requests for ten minutes. The database cancellation at the gateway is the durable authority across worker restarts; canceling HTTP alone is not sufficient. Missing inference identifiers remain temporarily accepted for gateway rollout compatibility; supplied identifiers must be valid. The cancellation endpoint always requires an identifier and the existing server credentials.

Success: `{ "text": "...", "durationSeconds": 123.4, "chunks": [], "model": "bark-3.0-plus" }`. Error statuses include 401 (authorization), 413 (size), 415 (type), 422 (audio/no speech), 429 (busy), 503 (unavailable), and 504 (timeout). The caller must check HTTP status; errors never contain upstream stack traces or transcript text.

Thirty-second disjoint windows bound inference memory for batch requests. Text is joined without filler removal or repetition deduplication. Plus can still miss audible fillers; it is not a perfect verbatim detector. The model is reused across requests, and the processor/config are loaded only from pinned local files. No remote code selection or runtime downloads are accepted. The reviewed publisher loader is SHA-256 checked; only its weight-decoding function is used, once during image build. Decoded tensors are saved without changing their values, then memory-mapped with `weights_only=True` at startup. Unused random weight initialization and redundant CPU copies are skipped; CPU math uses two threads. GPU inference remains FP32.

## Deployment

The provided Modal adapter is optional; it is configured for one worker, preferring L4 with the less expensive T4 as an ordered capacity fallback, two CPU cores, 8 GiB RAM, and sixty seconds of idle retention, with zero minimum containers. [Modal GPU fallback documentation](https://modal.com/docs/guide/gpu#gpu-fallbacks). Fallback expands the available capacity; it does not guarantee immediate scheduling or equal inference speed. Explicit concurrency of eight HTTP inputs lets cancellation enter while inference is busy; the application still admits only one inference at a time. The idle window lets quick retries reuse the loaded model; it does not shorten the first cold request or keep a worker warm through a five-minute recording. Do not deploy before setting a provider budget. Model build/loading and idle retention are billable as well as inference. The 120-second process deadline includes first model load; cold-start behavior must be measured before launch. Killing a request also discards the loaded model process, so the next request may need to load it again.

For the Neeley demo, stay on **Modal Starter** with its current $30/month included compute. The Workspace usage budget of **$30 gross** (before credits) and separate spend limit of **$0 net** (after credits) have both been verified in Usage & Billing. Preserve these caps; do not upgrade to Team or Enterprise. They do not fund the separate coaching API. The Supabase gateway separately admits up to $5/day in reserved demo requests ($0.075 batch speech, $0.30 live speech, and $0.060 coaching per request), not measured vendor charges. Sign-in preparation shares that daily allowance and has an additional bounded slice. [Budget and spend-limit definitions](https://modal.com/docs/guide/budgets), [Starter pricing](https://modal.com/pricing)

1. Use Python 3.11 and install `modal==1.6.2` in a dedicated environment; sign in to the chosen Modal account.
2. Create a Modal secret named `neeley-bark-worker`, containing `BARK_WORKER_TOKEN`. Generate a random URL-safe value with at least 32 random bytes (43 characters). Store that same value only in backend secrets.
3. From this directory run `modal deploy modal_app.py`. This builds dependencies and downloads fixed public model assets; it creates billable cloud infrastructure.
4. Create a Modal proxy-auth token. Proxy authentication is required and rejects unauthorized requests before a GPU container boots. Store its key/secret in the backend as `BARK_WORKER_MODAL_KEY` and `BARK_WORKER_MODAL_SECRET`.
5. Set backend `BARK_WORKER_URL` to the deployed HTTPS URL ending in `/transcribe`, plus `BARK_WORKER_TOKEN`. The gateway sends `Modal-Key` and `Modal-Secret` headers as well as Bearer authorization. None of these secrets belongs in frontend configuration or GitHub source.
6. Test real recordings, fillers, cancellation, ten-minute inputs, cold start, peak concurrency, and actual billed time. Non-GPU tests alone do not establish deployment readiness; the limited cloud smoke check below does not replace these launch checks.

## Cloud smoke check — October 26, 2026

The proxy-protected Modal deployment passed a 27.721875-second synthetic English fixture: **61.220 seconds cold** and **1.276 seconds warm**, measured from the client. Both outputs exactly matched its reference text, preserving two `um`, two `uh`, repeated `I, I`, and the complete ending. Missing proxy credentials returned 401, an incorrect worker bearer returned 401, and malformed WAV returned 422. The same fixture subsequently passed the authenticated browser flow through transcription, coaching, and saved-report reopening.

A **300-second** fixture, containing ten copies of that synthetic speech and 22.8 seconds of total gaps, completed through the public app. Modal reported **36.059 seconds of pre-start wait** and **54.461 seconds of execution, including lazy model loading**: 90.520 seconds from enqueue to completion. The button-to-enqueue interval was 6.577 seconds, giving a derived server completion at 97.10 seconds after the click. The UI was observed complete by 111.782 seconds. These metrics do not isolate container boot or pure inference time.

The five-minute output contained 728 words against 730 in the reference, with 19 of 20 expected `um` and a net count of 19 of 20 expected `uh`. Exact alignment found **four word edits**: one missing `um`, two missing `uh`, and one inserted `uh`; there were no other word edits. All ten `I, I` repetitions, all ten endings, and the final ending were intact. No warm five-minute run was measured. Repeated synthetic speech does not establish accuracy on human presentations or performance under concurrent students.

A later 60-second synthetic run at 7:07 p.m. Central on October 26 had **5.654 seconds of scheduling wait** and **12.865 seconds of execution**, or **18.519 seconds** from enqueue to completion. These measurements show substantial cold-start variability; the earlier 61-second run is not a current guaranteed baseline. Two separate warm runs of that minute-long fixture matched all 146 reference words, including its four `um`, four `uh`, and two repeated `I, I` phrases.

## T4 fallback check — October 27, 2026

A bounded ephemeral T4 worker ran the same 27.721875-second synthetic fixture twice using the unchanged FP32 `Bark` inference class. Model initialization, including dependency imports and moving weights to CUDA, took **14.528 seconds**. The first transcription took **1.541 seconds** and the second **0.392 seconds**. Both matched the reference words and preserved its two `um`, two `uh`, repeated `I, I`, and ending. Peak allocated GPU memory was **2,579.6 MiB**. The complete direct Modal dispatch, initialization, and two inference passes took **23.231 seconds**; this is not a public-app or HTTP end-to-end measurement. The ephemeral app was stopped afterward. This validates the fallback on one synthetic fixture, not long recordings or human-speech accuracy, and does not establish that T4 is always faster than L4. The dominant measured work was initialization.

For another GPU host: install `requirements.txt`, run `python models.py` during image build, set `BARK_WORKER_TOKEN`, then run `uvicorn server:create_app --factory --host 127.0.0.1 --port 8000 --no-access-log`. Put it behind a TLS reverse proxy that rejects unauthorized/oversized traffic, limits request rates, and has a finite request timeout. Do not expose the bare development server publicly. Use one Uvicorn worker per GPU; multiple processes duplicate model memory and bypass the local concurrency gate.

## Data handling and limits

Audio stays in RAM in this service; there are no audio temporary files. It is released after each request. The isolated inference process is killed on timeout or cancellation so GPU work cannot continue indefinitely. Uploads time out after 20 seconds within the overall 120-second request limit. Shared preparation is stopped when its last waiter leaves. The service does not log recordings, transcripts, keys, or provider responses; child-process output is suppressed. Deployment-platform metadata/log retention still follows the chosen host's configuration.

Supabase owns private saved rehearsal storage and retention. This worker stores neither rehearsal history nor analytics. Server authentication, per-user quotas, daily spending caps and job ownership must be enforced at the gateway; a shared worker credential is not student authorization. Never send it to a browser. A canceled browser request may still finish at the gateway, so use server job cancellation and measured usage accounting rather than promising zero charge after cancel.

## Tests without models or a GPU

In a dedicated Python environment, install `requirements-test.txt`, then run `python -m unittest discover -s tests -v` from this directory (or `python -m unittest discover -s cloud/speech-worker/tests -v` from the repository root). Tests cover strict WAV limits, complete segmentation, authorization, request size/type, safe errors, concurrency, timeout and real subprocess cancellation. They do not download weights or test CUDA accuracy. Direct runtime dependencies and model/config revisions are pinned; transitive dependency resolution and the base OS are not a reproducible lockfile yet.
